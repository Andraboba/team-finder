# TeamFinder

TeamFinder — платформа, на которой разработчики, дизайнеры и другие специалисты
находят единомышленников для совместной работы над pet-проектами. Пользователи
публикуют идеи проектов, присоединяются к чужим проектам и собирают команду.

Финальный проект курса (Яндекс Практикум), бэкенд на Django.

**Ветка `variant-2`: реализован вариант 2 — «Навыки» пользователей и фильтрация
участников по навыкам.** Вариант 1 («Избранное») находится в ветке `main`.

## Возможности

- Регистрация (имя, фамилия, email, пароль) и вход по email и паролю;
  при ошибке выводится «Неверный имейл или пароль». Выход — `GET /users/logout/`.
- При создании пользователя генерируется аватар: первая буква имени
  на случайном мягком однотонном фоне (Pillow).
- Список проектов (`/projects/list/`, корень `/` перенаправляет сюда):
  новые сверху, пагинация по 12.
- Страница проекта, создание и редактирование проекта (одна Django-форма,
  флаг `is_edit`), завершение проекта, участие и отказ от участия (AJAX).
  Автор проекта автоматически добавляется в участники.
- **Навыки пользователя** (модель `Skill`, поле `User.skills`, `skill.users`).
  На странице профиля блок «Навыки» видят все; владелец профиля может
  добавлять навыки через поле с автодополнением (до 10 подсказок, «Создать
  „…“», если точного совпадения нет) и удалять их крестиком — без перезагрузки
  страницы (`static/js/skills.js`). Эндпоинты:
  - `GET /users/skills/?q=<начало>` — до 10 навыков по алфавиту, название
    начинается с `q` (без учёта регистра), ответ `[{"id": …, "name": …}, …]`;
    выборка делается queryset-ом с `.values("id", "name")[:10]`;
  - `POST /users/<id>/skills/add` — в теле `skill_id` (существующий навык)
    или `name` (новый навык создаётся); только владелец профиля; ответ
    `{"skill_id": …, "created": true|false, "added": true|false}`
    (`added=false`, если навык уже был у пользователя);
  - `POST /users/<id>/skills/<skill_id>/remove/` — проверяются авторизация,
    владелец профиля, существование навыка и наличие его у пользователя;
    навык удаляется только из профиля, в БД он остаётся.
- **Пользователи** (`/users/list/`, пагинация по 12) с фильтром по навыкам:
  над сеткой панель «Фильтр по навыкам» со всеми навыками по алфавиту,
  клик по тегу даёт `?skill=<Название>`, остаются только пользователи с этим
  навыком (точное совпадение названия), активный тег подсвечен, рядом ссылка
  «Сбросить» на `/users/list`. Контекст шаблона: `participants`, `all_skills`,
  `active_skill` (плюс `page_obj` и `query_prefix` для пагинации).
- Профиль пользователя, редактирование профиля (имя, фамилия, аватар, о себе,
  телефон, GitHub), смена пароля.
- Валидация: телефон только `8XXXXXXXXXX` или `+7XXXXXXXXXX`, сохраняется в виде
  `+7XXXXXXXXXX`, уникален с учётом формата (8… и +7… считаются одним номером);
  ссылка на GitHub — корректный URL, ведущий именно на `github.com`.
- Права: создавать, редактировать и завершать проекты может только автор,
  участвовать — только авторизованные, менять навыки — только владелец профиля. Администратор через
  `/admin/` управляет пользователями (создание, блокировка через `is_active`,
  удаление, смена пароля) и любыми проектами.

## Стек

Python 3.13, Django 5.2, PostgreSQL 16 (Docker), Pillow, python-decouple,
gunicorn и whitenoise (для запуска в контейнере), flake8, GitHub Actions.

## Структура

```
team_finder/   настройки проекта, корневые urls
users/         модели User, UserManager и Skill, генерация аватара, формы,
               views (в т.ч. JSON-эндпоинты навыков), seed_data, тесты
projects/      модель Project, формы, views, JSON-эндпоинты, тесты
templates/     HTML-шаблоны варианта 2 (бывшая папка templates_var2)
static/        CSS, JS, шрифты, картинки
```

## Как запустить локально

1. Клонировать репозиторий и создать виртуальное окружение:

   ```bash
   git clone -b variant-2 https://github.com/Andraboba/team-finder.git team-finder-var2
   cd team-finder-var2
   python -m venv .venv
   # Windows (PowerShell): .venv\Scripts\Activate.ps1
   # Linux/macOS:          source .venv/bin/activate
   pip install -r requirements.txt
   ```

2. Создать `.env` по образцу и при необходимости поменять значения:

   ```bash
   cp .env_example .env
   ```

   | Переменная | Назначение |
   |---|---|
   | `DJANGO_SECRET_KEY` | секретный ключ Django |
   | `DJANGO_DEBUG` | режим отладки (`True` для разработки) |
   | `DJANGO_ALLOWED_HOSTS` | разрешённые хосты через запятую |
   | `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` | параметры БД |
   | `POSTGRES_HOST` | адрес БД (`localhost` при запуске Django на хосте) |
   | `POSTGRES_PORT` | порт БД на хосте (по умолчанию `5433`) |

   Если `POSTGRES_DB` не задан, Django использует SQLite (`db.sqlite3`) —
   это запасной вариант для быстрой проверки, основная БД — PostgreSQL.

3. Поднять PostgreSQL в Docker:

   ```bash
   docker compose up -d
   ```

   Порт на хосте берётся из `POSTGRES_PORT` (по умолчанию 5433, чтобы не
   конфликтовать с локально установленным PostgreSQL на 5432).

   Вариант 2 работает с отдельной базой `teamfinder_var2`, чтобы не смешивать
   схему с вариантом 1 (там есть «Избранное», а здесь — навыки). На новом
   томе база создаётся автоматически из `POSTGRES_DB`. Если контейнер
   `teamfinder_db` уже поднят из ветки `main` (вариант 1), достаточно создать
   вторую базу в нём же:

   ```bash
   docker exec teamfinder_db createdb -U team_finder -O team_finder teamfinder_var2
   ```

4. Применить миграции и загрузить тестовые данные:

   ```bash
   python manage.py migrate
   python manage.py seed_data
   ```

   `seed_data` создаёт суперпользователя, четырёх пользователей, по проекту
   (или два) у каждого, участия и навыки (15 навыков, у каждого пользователя
   3–5). Команда идемпотентна;
   `python manage.py seed_data --reset` пересоздаёт тестовые данные.

5. Запустить сервер разработки:

   ```bash
   python manage.py runserver
   ```

   Сайт будет доступен по адресу http://localhost:8000, админка —
   http://localhost:8000/admin/.

### Запуск целиком в Docker (необязательно)

```bash
docker compose --profile full up -d --build
docker compose exec web python manage.py seed_data
```

Контейнер `web` при старте выполняет `migrate` и `collectstatic`, затем
запускает gunicorn. Сайт будет на http://localhost:8001 (порт меняется
переменной `WEB_PORT`). Статику раздаёт whitenoise, медиа — Django; папка `media` общая с хостом.

## Тесты и проверка кода

```bash
python manage.py test
flake8 .
```

76 тестов (django `TestCase`) покрывают регистрацию и вход, генерацию аватара,
создание и редактирование проекта и права доступа, завершение проекта,
участие, модель навыков, автодополнение (алфавит, `startswith`, лимит 10),
добавление навыка по `skill_id` и по `name`, повторное добавление
(`added=false`), удаление, права чужого пользователя и анонима, CSRF,
фильтр `?skill=` (в том числе `C++` и пагинацию с фильтром), пагинацию,
валидацию телефона и ссылки на GitHub, смену пароля. В GitHub Actions
(`.github/workflows/ci.yml`) на каждый push в `main` и `variant-2` запускаются flake8, проверка
миграций и тесты на PostgreSQL.

## Отклонения от рекомендаций и почему

- **Шаблоны.** Папка `templates_var2` переименована в `templates`, папки
  других вариантов удалены. Из шаблонов варианта 2 убраны неиспользуемые
  остатки «Избранного» (`favorite_projects.html`, `project-fav-toggle.js`):
  в варианте 2 этой функциональности нет, как и `/projects/favorites/`,
  `toggle-favorite` и фильтров `?filter=`.
- **`User.skills` — ManyToMany, а не внешний ключ.** В задании поле названо
  «внешним ключом на Skill», но пользователь владеет многими навыками, а
  у навыка должно быть много пользователей (`skill.users`), поэтому это
  `ManyToManyField(Skill, related_name="users", blank=True)`.
- **Уникальное название навыка.** `Skill.name` уникально; при добавлении по
  `name` сначала ищется существующий навык без учёта регистра
  (`python` → `Python`), чтобы не плодить дубликаты.
- **Ответ `skills/add`.** Помимо `skill_id`, `created`, `added` возвращаются
  `id` и `name`: их читает `skills.js`, чтобы сразу нарисовать новый тег.
  Эндпоинт принимает и JSON (так шлёт `skills.js`), и обычные form-data.
- **Слэш в конце URL.** В задании `.../skills/add` без слэша, а `skills.js`
  отправляет `.../skills/add/`; оба варианта (и для `skills/`, `remove/`)
  принимаются.
- **Коды ошибок навыков** (всегда JSON): `401` — аноним, `403` — чужой
  профиль, `404` — нет пользователя или навыка, `400` — пустые/некорректные
  параметры, название длиннее 124 символов или навыка нет у пользователя.
- **Безопасность `skills.js`.** Новый тег создаётся через `textContent`
  вместо `innerHTML`, чтобы название навыка не исполнялось как HTML.
  В `skills.css` добавлено правило `.add-skill-btn.hidden`, иначе кнопка
  «+ Добавить навык» не пряталась при открытом поле ввода.
- **Ссылки фильтра.** В `participants.html` название навыка в ссылке
  кодируется (`?skill={{ skill.name|urlencode }}`), иначе навыки вроде
  `C++` или `C#` ломали бы фильтр. `active_skill` — объект `Skill`
  (шаблон сравнивает его с тегом); для несуществующего навыка — строка,
  при этом список пуст и показывается «Сбросить».
- **Страница профиля** помечена `ensure_csrf_cookie`, чтобы `skills.js`
  всегда мог взять CSRF-токен из cookie.
- **Телефон.** По рекомендациям поле обязательное, но при регистрации телефон не
  запрашивается. Поэтому в БД допускается пустая строка, а уникальность
  непустых номеров обеспечивает условное ограничение `UniqueConstraint`
  (`phone != ''`) плюс проверка в форме с учётом нормализации к `+7`.
- **Email.** При регистрации email приводится к нижнему регистру, вход
  не зависит от регистра.
- **Порядок пользователей.** В описании страницы сказано «от новых к старым»,
  в рекомендациях — «по id». Используется сортировка по id по убыванию:
  это одновременно и порядок добавления в БД, и «новые сверху».
- **Контекст `projects` на главной** содержит проекты текущей страницы
  (`page_obj.object_list`), а не весь queryset: шаблон проверяет
  `{% if projects %}`, и так не нужно загружать все проекты из БД.
  Для пагинации передаются `page_obj` и `query_prefix`.
- **Поле `date_joined`** добавлено в модель User для админки (дата регистрации).
- **Статусы проекта** хранятся как `open`/`closed` (choices `Open`/`Closed`
  по заданию), а в выпадающем списке формы показываются «Открыт»/«Закрыт».
- **Завершение проекта** возвращает `403`, если запрос отправил не автор,
  `400`, если проект уже закрыт, и `401` для анонима (во всех случаях JSON).
  Редактирование чужого проекта — `403`.
- **Валидаторы паролей** включены только при `DJANGO_DEBUG=False` (как
  в исходной заготовке), чтобы при разработке можно было использовать простые
  пароли.
