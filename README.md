# TeamFinder

TeamFinder — платформа, на которой разработчики, дизайнеры и другие специалисты
находят единомышленников для совместной работы над pet-проектами. Пользователи
публикуют идеи проектов, присоединяются к чужим проектам и собирают команду.

Финальный проект курса (Яндекс Практикум), бэкенд на Django.

**Ветка `variant-3`: реализован вариант 3 — «Необходимые навыки» проектов
и фильтрация проектов по навыкам.** Вариант 1 («Избранное» и фильтры
пользователей) находится в ветке `main`.

## Возможности

- Регистрация (имя, фамилия, email, пароль) и вход по email и паролю;
  при ошибке выводится «Неверный имейл или пароль». Выход — `GET /users/logout/`.
- При создании пользователя генерируется аватар: первая буква имени
  на случайном мягком однотонном фоне (Pillow).
- Список проектов (`/projects/list/`, корень `/` перенаправляет сюда):
  новые сверху, пагинация по 12.
- Страница проекта, создание и редактирование проекта (одна Django-форма,
  флаг `is_edit`), завершение проекта, участие и отказ от участия (AJAX).
  Автор проекта автоматически добавляется в участники.
- **Необходимые навыки проекта.** На странице проекта блок «Необходимые навыки»
  с тегами. Смотреть его могут все, управлять — только автор проекта:
  кнопка «+ Добавить навык», поле с автодополнением (до 10 подсказок),
  пункт «Создать „…“» для нового навыка, крестик для удаления. Всё работает
  без перезагрузки страницы (`static/js/skills.js`).
  - `GET /projects/skills/?q=<начало>` — первые 10 навыков по алфавиту,
    название которых начинается с `q` (без учёта регистра):
    `[{"id": 1, "name": "Django"}, ...]`. Фильтрация, сортировка и `LIMIT`
    выполняются в SQL, выбираются только `id` и `name` (`.values()`).
  - `POST /projects/<id>/skills/add/` (работает и без завершающего слэша) —
    в теле `skill_id` (существующий навык) или `name` (новый навык); JSON или
    обычная форма. Ответ: `{"skill_id": 5, "created": false, "added": true, ...}`.
    `added=false`, если навык уже есть у проекта.
  - `POST /projects/<id>/skills/<skill_id>/remove/` — убирает навык из проекта;
    сам навык остаётся в БД и доступен другим проектам.
  - Ошибки — JSON: `401` аноним, `403` не автор проекта, `404` нет проекта или
    навыка, `400` неверные параметры или навыка нет у проекта.
- **Фильтр проектов по навыкам** на главной: панель «Фильтр по необходимым
  навыкам» со всеми навыками по алфавиту, клик формирует `?skill=<название>`,
  активный тег подсвечивается, «Сбросить» ведёт на `/projects/list`.
  Остаются проекты, у которых есть навык с точно таким названием.
  Пагинация сохраняет параметр `skill`.
- **Пользователи** (`/users/list/`) — все активные пользователи, пагинация
  по 12, без фильтров.
- Профиль пользователя, редактирование профиля (имя, фамилия, аватар, о себе,
  телефон, GitHub), смена пароля.
- Валидация: телефон только `8XXXXXXXXXX` или `+7XXXXXXXXXX`, сохраняется в виде
  `+7XXXXXXXXXX`, уникален с учётом формата (8… и +7… считаются одним номером);
  ссылка на GitHub — корректный URL, ведущий именно на `github.com`.
- Права: создавать, редактировать и завершать проекты и управлять их
  навыками может только автор, участвовать — только авторизованные. Администратор через
  `/admin/` управляет пользователями (создание, блокировка через `is_active`,
  удаление, смена пароля) и любыми проектами.

## Стек

Python 3.13, Django 5.2, PostgreSQL 16 (Docker), Pillow, python-decouple,
gunicorn и whitenoise (для запуска в контейнере), flake8, GitHub Actions.

## Структура

```
team_finder/   настройки проекта, корневые urls
users/         модель User и UserManager, генерация аватара, формы, views,
               команда seed_data, тесты
projects/      модели Project и Skill, формы, views, JSON-эндпоинты навыков,
               тесты
templates/     HTML-шаблоны варианта 3 (из папки templates_var3 заготовки)
static/        CSS, JS, шрифты, картинки
```

## Как запустить локально

1. Клонировать репозиторий и создать виртуальное окружение:

   ```bash
   git clone -b variant-3 https://github.com/Andraboba/team-finder.git team-finder-var3
   cd team-finder-var3
   python -m venv .venv
   # Windows (PowerShell): .venv\Scripts\Activate.ps1
   # Linux/macOS:          source .venv/bin/activate
   pip install -r requirements.txt
   ```

2. Создать `.env` по образцу и при необходимости поменять значения:

   ```bash
   cp .env_example .env
   ```

   | Переменная | Назначение |
   |---|---|
   | `DJANGO_SECRET_KEY` | секретный ключ Django |
   | `DJANGO_DEBUG` | режим отладки (`True` для разработки) |
   | `DJANGO_ALLOWED_HOSTS` | разрешённые хосты через запятую |
   | `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` | параметры БД |
   | `POSTGRES_HOST` | адрес БД (`localhost` при запуске Django на хосте) |
   | `POSTGRES_PORT` | порт БД на хосте (по умолчанию `5433`) |

   Если `POSTGRES_DB` не задан, Django использует SQLite (`db.sqlite3`) —
   это запасной вариант для быстрой проверки, основная БД — PostgreSQL.

3. Поднять PostgreSQL в Docker:

   ```bash
   docker compose up -d
   ```

   Порт на хосте берётся из `POSTGRES_PORT` (по умолчанию 5433, чтобы не
   конфликтовать с локально установленным PostgreSQL на 5432).
   Для варианта 3 используется отдельная база `teamfinder_var3`. Если контейнер
   `teamfinder_db` уже создан для другого варианта (с другой базой), создайте
   базу вручную:

   ```bash
   docker exec teamfinder_db psql -U team_finder -d postgres -c "CREATE DATABASE teamfinder_var3"
   ```

4. Применить миграции и загрузить тестовые данные:

   ```bash
   python manage.py migrate
   python manage.py seed_data
   ```

   `seed_data` создаёт суперпользователя, четырёх пользователей, по проекту
   (или два) у каждого, участия, справочник из 16 навыков и необходимые
   навыки у каждого проекта. Команда идемпотентна;
   `python manage.py seed_data --reset` пересоздаёт тестовые данные.

5. Запустить сервер разработки:

   ```bash
   python manage.py runserver 8003
   ```

   Сайт будет доступен по адресу http://localhost:8003, админка —
   http://localhost:8003/admin/ (порт любой; 8003 выбран, чтобы вариант 3
   можно было запускать одновременно с другими вариантами).

### Запуск целиком в Docker (необязательно)

```bash
docker compose --profile full up -d --build
docker compose exec web python manage.py seed_data
```

Контейнер `web` при старте выполняет `migrate` и `collectstatic`, затем
запускает gunicorn. Сайт будет на http://localhost:8001 (порт меняется
переменной `WEB_PORT`). Статику раздаёт whitenoise, медиа — Django; папка `media` общая с хостом.

## Тесты и проверка кода

```bash
python manage.py test
flake8 .
```

73 теста (django `TestCase`) покрывают регистрацию и вход, генерацию аватара,
создание и редактирование проекта и права доступа, завершение проекта,
участие, навыки проектов (автодополнение: `startswith`, алфавитный порядок,
лимит 10; добавление по `skill_id` и по `name`, повторное добавление с
`added=false`, удаление с сохранением навыка в БД, права автора, анонима и
чужого пользователя, ошибки 400/404/405), фильтр `?skill=` с точным
совпадением и сохранением в пагинации, пагинацию, валидацию телефона и
ссылки на GitHub, смену пароля. В GitHub Actions
(`.github/workflows/ci.yml`) на каждый push в `main` и `variant-3` запускаются
flake8, проверка миграций и тесты на PostgreSQL.

## Отклонения от рекомендаций и почему

- **Шаблоны.** Папка `templates_var3` заготовки стала папкой `templates`,
  папки других вариантов удалены; переменная `TASK_VERSION` не нужна. Из
  шаблонов убраны остатки «Избранного», которые в варианте 3 не используются
  (`favorite_projects.html`, `includes/project-fav-toggle.js` и его подключение
  на главной).
- **Связь `Project.skills`.** В рекомендациях поле описано как «внешний ключ на
  модель Skill», но у проекта может быть несколько навыков, а у навыка —
  несколько проектов (`skill.projects`), поэтому это `ManyToManyField(Skill,
  related_name="projects", blank=True)`.
- **Уникальность навыков.** `Skill.name` уникально, а при добавлении по `name`
  существующий навык ищется без учёта регистра (`python` → `Python`), чтобы в
  справочнике не было дублей; новый навык при этом не создаётся
  (`created=false`).
- **Ответ `skills/add`.** Помимо требуемых `skill_id`, `created`, `added` в
  ответ добавлены `id` и `name`: их читает `static/js/skills.js`, чтобы
  нарисовать новый тег.
- **URL добавления навыка.** В задании — `/projects/<id>/skills/add`, в
  `skills.js` — `/projects/<id>/skills/add/`; работают оба адреса.
- **Тело запроса.** `skills.js` отправляет JSON, поэтому эндпоинт принимает
  JSON, а также обычные form-data.
- **Фильтр по навыкам.** В контекст `all_skills` передаются названия навыков
  (строки, по алфавиту): шаблон выводит `{{ skill }}` и сравнивает его с
  `active_skill` (строка из `?skill=`), поэтому подсветка работает при
  сравнении строк. В ссылке тега добавлен фильтр `urlencode`, иначе навыки
  вида `C++` или `C#` ломали бы параметр.
- **Автодополнение** ищет без учёта регистра (`istartswith`), а фильтр
  `?skill=` — по точному совпадению названия, как требует задание.
- **Ответы навыковых эндпоинтов** — JSON: `401` анониму, `403` не автору,
  `404`, если нет проекта или навыка, `400`, если навыка нет у проекта или
  параметры неверны.
- **Телефон.** По рекомендациям поле обязательное, но при регистрации телефон не
  запрашивается. Поэтому в БД допускается пустая строка, а уникальность
  непустых номеров обеспечивает условное ограничение `UniqueConstraint`
  (`phone != ''`) плюс проверка в форме с учётом нормализации к `+7`.
- **Email.** При регистрации email приводится к нижнему регистру, вход
  не зависит от регистра.
- **Порядок пользователей.** В описании страницы сказано «от новых к старым»,
  в рекомендациях — «по id». Используется сортировка по id по убыванию:
  это одновременно и порядок добавления в БД, и «новые сверху».
- **Контекст `projects` на главной** содержит проекты текущей страницы
  (`page_obj.object_list`), а не весь queryset: шаблон проверяет
  `{% if projects %}`, и так не нужно загружать все проекты из БД.
  Для пагинации передаются `page_obj` и `query_prefix` (`skill=<навык>&`
  при активном фильтре).
- **Поле `date_joined`** добавлено в модель User для админки (дата регистрации).
- **Статусы проекта** хранятся как `open`/`closed` (choices `Open`/`Closed`
  по заданию), а в выпадающем списке формы показываются «Открыт»/«Закрыт».
- **Завершение проекта** возвращает `403`, если запрос отправил не автор,
  `400`, если проект уже закрыт, и `401` для анонима (во всех случаях JSON).
  Редактирование чужого проекта — `403`.
- **Валидаторы паролей** включены только при `DJANGO_DEBUG=False` (как
  в исходной заготовке), чтобы при разработке можно было использовать простые
  пароли.
